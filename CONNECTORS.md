# MCP connector support

Connect AI has one persisted MCP connection registry. The server-owned definitions in `server/src/main/resources/catalog/mcp-catalog.json` drive the Tools catalog and connection-method choices. A catalog card is not proof that a vendor integration is configured. For token and no-auth connections, the wizard tests a temporary MCP handshake and tool discovery before saving, then creates the persistent session and exposes only tools actually reported by that server.

## Current support in this repository

| Catalog entry | Current path | Status |
| --- | --- | --- |
| GitHub | GitHub.com hosted MCP over bearer PAT or a preconfigured GitHub OAuth app | PAT and OAuth tokens are stored encrypted. OAuth success waits for authenticated MCP initialize and tools/list. Fake OAuth/MCP only; no live-provider test. The app uses static provider settings and does not discover OAuth metadata. |
| Google Drive | Official Drive MCP endpoint over static Google OAuth | Callback now exchanges the code, stores/refreshes tokens encrypted, then automatically initializes MCP and discovers tools before success is reported. Fake OAuth/MCP tested; no live-provider test. Requires Workspace Developer Preview membership and Google Cloud setup. |
| Jira | `mcp-atlassian` running separately on the configured local endpoint; its Jira credentials belong to that MCP process | Local MCP required; Connect AI does not host or provision that server. |
| Linear | Documented hosted endpoint; bearer token | Generic MCP bearer connection can test and discover tools. OAuth discovery is marked unsupported. |
| Atlassian | Documented Rovo MCP endpoint; Basic email/API-token method | Catalog enables Basic authentication. This path has not been verified against a live Atlassian tenant and may require organization-admin enablement. OAuth discovery remains unsupported. |
| Grafana | Grafana Cloud hosted MCP over Streamable HTTP with OAuth 2.1 (PKCE); self-hosted OSS `mcp-grafana` with per-request Grafana instance and service-account headers remains available | Hosted OAuth uses the preregistered OAuth client values generated by Grafana Cloud. Self-hosted MCP endpoints are operated by the user. Actual tools are discovered from the connected server. Fake MCP only. |
| Splunk | User supplies the endpoint copied from the Splunk MCP Server app and its encrypted MCP token as bearer | Generic MCP lifecycle works. An ordinary Splunk URL/token is not equivalent. Fake MCP only. |
| PagerDuty | Hosted `https://mcp.pagerduty.com/mcp`; Authorization custom header | The shared custom-header transport can send `Authorization: Token token=…`; a successful MCP handshake is required before saving. Fake MCP only. |
| Datadog | User supplies site-specific hosted endpoint; `DD_API_KEY` and `DD_APPLICATION_KEY` custom headers | Multi-header auth is supported and verifies via MCP. OAuth 2.1 is not implemented. Fake MCP only; endpoint must be copied from Datadog's site selector. |
| Notion | Not offered as a direct connect method | Notion MCP is hosted and consent-based, but this backend does not implement its MCP OAuth discovery / authorization exchange. Use another supported MCP client until this app implements that protocol. |
| Slack | Slack's official remote Streamable HTTP MCP at `https://mcp.slack.com/mcp`, using confidential user-token OAuth and `Authorization: Bearer` | Uses the documented `oauth/v2_user/authorize` and `oauth.v2.user.access` flow with S256 PKCE, state, a resource indicator, secure server-side token storage, then real MCP initialization and tools/list. Requires `SLACK_OAUTH_CLIENT_ID`, `SLACK_OAUTH_CLIENT_SECRET`, and a provider-specific HTTPS `SLACK_OAUTH_REDIRECT_URI`. Slack currently permits only internal or Marketplace-published apps to access its MCP service. Fake OAuth/MCP test only; no live Slack test. |
| Custom MCP | User supplies endpoint; None, bearer, Basic, custom header, or multiple headers | Generic Streamable HTTP methods implemented. OAuth discovery is disabled. Test and save use the shared API. |

The backend currently accepts `STREAMABLE_HTTP`; stdio and SSE are not supported by this connection path. Static OAuth provider IDs are configured on the server and exposed through `/api/oauth/providers`. Protected-resource metadata discovery and dynamic client registration are not implemented; Slack's endpoints/resource are configured from its official metadata in the backend instead. The catalog endpoint computes supported methods and status from the backend configuration and runtime state; the UI does not infer OAuth readiness from a catalog card alone. OAuth completion remains pending until authenticated MCP initialize and bounded tools/list discovery have succeeded.

### Grafana

Grafana Cloud is the default one-button flow: Connect AI connects to `https://mcp.grafana.com/mcp` and authorizes the signed-in Grafana user with OAuth 2.1 and PKCE S256. Grafana Cloud may ask the user to enter a stack URL during authorization; that is part of Grafana's hosted flow. An administrator must register Connect AI under Grafana Assistant > Settings > Connectors > MCP clients, choose Read only access, configure the generated values as backend `GRAFANA_OAUTH_CLIENT_ID`, `GRAFANA_OAUTH_CLIENT_SECRET`, `GRAFANA_OAUTH_AUTHORIZE_URL`, `GRAFANA_OAUTH_TOKEN_URL`, and `GRAFANA_OAUTH_SCOPES`, and register the exact `CONNECTAI_OAUTH_REDIRECT_URI` callback. Set `GRAFANA_OAUTH_CLIENT_AUTHENTICATION` only if the registered client uses a method other than the default `client_secret_basic`. Dynamic Client Registration is not implemented, so the one-time administrator setup is required before users can use the sign-in button. Restart the backend after setting these environment variables.

The self-hosted option remains available for the official open-source `mcp-grafana` server over Streamable HTTP. Create a Grafana service account and a token with least-privilege read access for the tool categories you intend to expose. Enter the URL of that instance, the service-account token, and the Streamable HTTP URL of your trusted `mcp-grafana` deployment. If that MCP endpoint has caller authentication, enter its separate bearer token. Connect AI sends the Grafana values as `X-Grafana-URL` and `X-Grafana-Service-Account-Token`, encrypts them in its connection configuration, and does not return them from APIs. The MCP server must be configured for per-request instance selection with `--allow-grafana-url-override` and an exact `--allowed-grafana-urls` value. For a single-instance server, protect the endpoint with `--server-auth-token` and allow only that Grafana URL. For a shared multi-instance server, use an authenticated proxy that binds each caller to an approved URL and matching credential. Keep TLS verification enabled, restrict outbound network access, and configure the server with `--disable-write` where supported.

Run the official MCP server with Streamable HTTP and `--disable-write`. Connect AI independently filters tools carrying a write annotation or mutating tool names from investigations by default (`connectai.agent.allow-write-tools=false`). MCP tool availability is still controlled by the installed Grafana version, enabled server tool categories, and the service account's RBAC permissions. The wizard requires a successful initialize and non-empty live `tools/list` result before saving; its Connected state reflects a live session. Connection details allow replacing the Grafana URL and tokens, which disconnects before re-encrypting and reconnecting. See [Grafana MCP options](https://grafana.com/docs/grafana/latest/developer-resources/mcp/), [authentication](https://grafana.com/docs/grafana/latest/developer-resources/mcp/configure/authentication/), [Streamable HTTP transports](https://grafana.com/docs/grafana/latest/developer-resources/mcp/configure/transports-and-addresses/), [read-only and tool categories](https://grafana.com/docs/grafana/latest/developer-resources/mcp/configure/enable-and-disable-tools/), and [command-line flags and URL selection security](https://grafana.com/docs/grafana/latest/developer-resources/mcp/configure/command-line-flags/).
For self-hosted private targets, Connect AI also requires `CONNECTAI_MCP_ALLOW_PRIVATE_HOSTS=true`; link-local and metadata targets are always rejected by the application. The connection wizard requires a successful initialize and live `tools/list` result before saving. See [Grafana Cloud MCP](https://grafana.com/docs/grafana-cloud/ai-tools/mcp-servers/cloud-mcp/), [OAuth client registration](https://grafana.com/docs/grafana-cloud/ai-tools/mcp-servers/register-oauth-client/), and [open-source Grafana MCP](https://grafana.com/docs/grafana/latest/developer-resources/mcp/).

Google Drive setup: a server administrator enables Drive API and Drive MCP API, enrolls the project in Workspace Developer Preview, configures the OAuth consent screen (Internal or External with test users), registers the Drive scopes in Google Auth Platform Data Access, and sets backend `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET`. Add the app callback URI as an authorized redirect URI: local default `http://localhost:8080/connect-ai/api/oauth/callback`; production must use the HTTPS URI configured by `CONNECTAI_OAUTH_REDIRECT_URI`. The runtime requests `https://www.googleapis.com/auth/drive.readonly`; Google’s setup guide asks administrators to list both `drive.readonly` and `drive.file` in Data Access. See [Configure the Drive MCP server](https://developers.google.com/workspace/drive/api/guides/configure-mcp-server).

GitHub: create a fine-grained PAT with only the repository and organization read permissions needed, paste it into the GitHub catalog wizard, and let the wizard verify the actual remote MCP handshake. GitHub's remote host is `https://api.githubcopilot.com/mcp/`. OAuth is available only when the backend has `GITHUB_OAUTH_CLIENT_ID` and `GITHUB_OAUTH_CLIENT_SECRET`; the registered callback must exactly match `CONNECTAI_OAUTH_REDIRECT_URI` (local default `http://localhost:8080/connect-ai/api/oauth/callback`). This application uses a preconfigured authorization-code client and does not perform OAuth metadata discovery. The callback still proves the token against the real MCP endpoint before reporting success. See the [GitHub MCP host integration guide](https://github.com/github/github-mcp-server/blob/main/docs/host-integration.md).

Slack: configure `SLACK_OAUTH_CLIENT_ID`, `SLACK_OAUTH_CLIENT_SECRET`, and `SLACK_OAUTH_REDIRECT_URI` in the backend environment. The exact callback path is `/connect-ai/api/oauth/callback`; the configured full redirect URI must be HTTPS and must match Slack's OAuth & Permissions > Redirect URLs exactly. Slack does not accept the application's local HTTP callback, so local development needs an HTTPS tunnel forwarding to backend port 8080 and the same callback path. Enable PKCE (S256) in the Slack app. The OAuth request uses the Slack user-token endpoints and resource `https://mcp.slack.com`; requested scopes are `search:read.public`, `search:read.private`, `channels:history`, and `groups:history` to support message search plus channel/thread reads without write scopes. Slack's official MCP service is restricted to internal or Marketplace-published apps; workspace approval/install requirements remain controlled by Slack. See [Slack MCP server](https://docs.slack.dev/ai/slack-mcp-server/), [Slack OAuth v2](https://docs.slack.dev/authentication/installing-with-oauth/), and [Slack user-token exchange](https://docs.slack.dev/reference/methods/oauth.v2.user.access/).

PagerDuty: use the hosted endpoint and enter an API key in the Authorization header value using the documented `Token token=<key>` syntax. See [PagerDuty remote MCP](https://docs.pagerduty.com/developer/mcp-tooling-remote-server).

Datadog: choose the MCP endpoint for the account's site in Datadog's setup page. Configure custom headers exactly named `DD_API_KEY` and `DD_APPLICATION_KEY`, with scoped keys and `mcp_read` plus resource-level read permissions. Connect AI implements this header method, not Datadog's OAuth discovery. See [Datadog MCP setup and authentication](https://docs.datadoghq.com/mcp_server/setup/).

Splunk: the administrator installs/configures the Splunk MCP Server app and grants `mcp_tool_execute`; users generate an encrypted MCP token in that app (own token creation requires `edit_tokens_own` and `mcp_tool_admin`). Enter the MCP endpoint copied from that app and the encrypted token. Do not use the platform URL or an ordinary Splunk token. See [Splunk MCP connection settings](https://help.splunk.com/en/splunk-enterprise/mcp-server-for-splunk-platform/1.1/connecting-to-the-mcp-server-and-settings).

## Adding a connector

1. Add a definition to `server/src/main/resources/catalog/mcp-catalog.json` and keep keys stable. The server validates required metadata and method names at startup.
2. Mark only implemented authentication methods as supported. The shared connection client currently implements None, bearer, Basic, one custom header, and multiple headers. Only static OAuth app configuration is supported; protected-resource discovery/DCR is not.
3. Keep endpoint variants and provider claims accurate. An endpoint in the catalog does not establish that the tenant is enabled, the endpoint is reachable, or its discovered tools are read-only.
4. For static OAuth, add provider settings under `connectai.oauth.providers.<id>`. Keep deployed client secrets in backend environment variables. For local development, copy `server/config-example/application.yml` to the git-ignored `server/config/application.yml` and edit it; Spring Boot reads it when the backend starts from `server/`. `CONNECTAI_OAUTH_REDIRECT_URI` is the exact provider callback; `CONNECTAI_FRONTEND_ORIGIN` is the exact callback-message destination. Reuse the existing OAuth resource/service.
5. Add fake HTTP/MCP tests for methods, handshake, discovery, callback/token handling, errors, and secret redaction. Live provider verification requires configured credentials and explicit user authorization.

## Credentials and recovery

Bearer credentials are encrypted by the backend with `CONNECTAI_ENCRYPTION_KEY`; keep that key stable and back it up securely. Changing it makes existing ciphertext unreadable. Connect AI cannot recover an old plaintext token from ciphertext encrypted with a different key. For a BEARER connection, Tools → connection details → **Replace token** stores a newly supplied credential encrypted under the current key, then attempts a fresh MCP handshake. OAuth credentials must be renewed through the provider sign-in flow. Secrets are never returned by the connection API.

## Known limits

- There is no arbitrary transport/auth negotiation or dynamic OAuth client registration.
- Catalog entries do not imply that a vendor MCP endpoint exists, is enabled, or is read-only. Inspect the tools actually discovered and their permissions before relying on them.
- OAuth scopes do not by themselves guarantee read-only MCP tools. The investigation tool filtering and provider-side permissions remain important safeguards.
- Local/manual integrations require the external MCP process and its own service credentials to be installed and managed.
- OAuth callback tool discovery is server-side; the UI reads the final attempt status and fetches already discovered tools. Token audience/issuer validation is provider-specific and not implemented generically; each provider must be tested with its real endpoint before production use.
- `CONNECTAI_MCP_ALLOW_PRIVATE_HOSTS=true` is required for private/local MCP addresses. DNS is checked before connecting, but a DNS change between validation and client resolution cannot be fully pinned by the current JDK HTTP stack.
# Optional semantic tool retrieval

The investigation planner always uses the live connected MCP catalog and its deterministic exact/lexical matching. Semantic retrieval can augment LLM and rule-based planner candidates when enabled; it never makes a stale or disconnected tool executable. Investigation question text is sent to the configured Ollama embedding endpoint, so keep that endpoint local or use an endpoint approved for this data.

To enable it:

1. Use PostgreSQL with the pgvector extension installed, then run `CREATE EXTENSION vector` in the Connect AI database before starting the application. The Liquibase changeset creates the embedding table only when that extension exists and remains pending otherwise.
2. Run a local Ollama server and install an embedding model, for example `ollama pull nomic-embed-text`.
3. Set `CONNECTAI_SEMANTIC_RETRIEVAL_ENABLED=true`. Optional settings are `CONNECTAI_EMBEDDING_OLLAMA_BASE_URL` (defaults to `OLLAMA_BASE_URL` or `http://localhost:11434`), `CONNECTAI_EMBEDDING_MODEL` (defaults to `nomic-embed-text`), and `CONNECTAI_EMBEDDING_TIMEOUT_SECONDS` (defaults to `10`).
4. Restart the backend. Tool descriptions are embedded and cached by server, tool name, model, metadata format version and content hash; each investigation query is embedded at planning time. If pgvector, the table, or Ollama is unavailable, the planner falls back to exact/lexical retrieval and logs that semantic retrieval was skipped.

Ollama uses its documented `POST /api/embed` endpoint and supports batched text inputs ([Ollama embedding API](https://docs.ollama.com/api/embed)). pgvector supports exact nearest-neighbor search and the cosine-distance operator used by the current query ([pgvector documentation](https://github.com/pgvector/pgvector)). The implementation currently uses exact search; it does not create an approximate index until a representative workload justifies one.

This optional path has not been live-tested in this environment because the PostgreSQL server and pgvector extension are not available to the test suite. Its default remains disabled; the existing lexical path is used unless explicitly configured. There is no representative relevance benchmark yet, so no retrieval-quality improvement is claimed.
